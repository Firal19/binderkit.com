# binderkit.com

The Binderkit landing page. Binder setup for care homes.

A front page, its marketing pages, one stylesheet, one script, no framework
and no runtime dependencies. `node build.mjs` writes `dist/` and `dist/` is
the site.

## Run it

```sh
node build.mjs          # → dist/
node tools/check.mjs    # what has to be true of the built bytes
node tools/serve.mjs    # http://localhost:4321
```

Two local tools need a browser and are not part of the build:

```sh
node tools/icons.mjs    # the app icons and the social card → src/assets/raster/
node tools/shots.mjs    # every width, light and dark → review/
```

Both find Playwright on their own, or take `PLAYWRIGHT=/path/to/playwright`.

| | |
|---|---|

| `src/data/states.js` | the four words this product owns for its own states |
| `src/render/pages/<id>.js` | the site: its header, its footer, the front page and every marketing page it exports |
| `src/css/pages/<id>.css` | its face — fonts, palette, layout, motion, mobile, dark, print |
| `src/js/pages/<id>.js` | its own interactivity, appended after the shared script |
| `src/render/icons/<id>.js` | its own icon set |
| `src/features/<id>.js` | the twenty-five site features, each with a probe `tools/check.mjs` verifies against the built bytes |
| `src/render/shared.js` | the few pieces every page shares: the two forms, the FAQ, the social block, the byline |
| `src/render/social.js` · `src/data/social.js` | the eight platforms and the family's handles |
| `src/render/instruments.js` | the product surfaces the page shows, rendered in HTML |
| `src/marks.js` | the five marks, three bodies each |
| `src/css/faces.css` | the face package, generated by the system board |
| `src/css/base.css` | the reset, the form and the small “By Providerhub Oregon” lockup |
| `api/waitlist.js` · `api/contact.js` · `api/inbound.js` | the three endpoints: the list, the contact form, and where email to this domain arrives |
| `lib/mail.js` | the one way the site sends an email, and the letters it writes |
| `convex/` | three tables: the list, the messages, the inbox log |

The instruments on the page — the phone, the desktop, the printed sheet — are the product’s own screens rendered in HTML; `src/css/faces.css` is generated by the system board at [bydesign.providerhub.us](https://bydesign.providerhub.us) and gives them their values. The page around them is this product’s own design and nobody else’s.

## Email — one inbox for the whole family

Every message this site sends leaves as `hello@binderkit.com`; every message sent
to any address at `binderkit.com` is received by Resend, relayed whole to one
inbox with reply-to set to the sender, and logged. Answering is an ordinary
reply. Environment on the Vercel project:

| | |
|---|---|
| `CONVEX_URL` | `https://<deployment>.convex.cloud` — the list and the messages; required for the waitlist |
| `RESEND_API_KEY` | lets the site write and read mail |
| `RESEND_WEBHOOK_SECRET` | signs the `email.received` webhook that `/api/inbound` verifies |
| `MAIL_INBOX` | the one inbox every notice and every received email is copied to |
| `MAIL_DOMAIN` | `binderkit.com` — the sending domain, for previews on another host |

`tools/mail-setup.mjs` sets all of it, for all four sites, from one
full-access Resend key. With Resend unset the endpoints still keep the row
and say so; with `CONVEX_URL` unset the waitlist answers 503 rather than
pretending.

- `POST /api/waitlist` `{ email, track, houses, product }` → one row, a receipt to the signer, a notice to the inbox.
- `POST /api/contact` `{ name, email, topic, message, product }` → one row, a receipt, a notice whose reply-to is the writer.
- `POST /api/inbound` — Resend's signed webhook; fetches the message and relays it.

Read the lists with `waitlist:list`, `mail:messages` and `mail:received`,
which want the `WAITLIST_KEY` set in the Convex environment.
